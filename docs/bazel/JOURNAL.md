# Bazel integration journal

A reproducible record of how this fork was moved to Bazel: what was done, with which
commands, what went wrong, and what carries over to other Autoware-based or plain ROS 2
projects. Goals and decisions (the *why*) live in [PLAN.md](PLAN.md); this file is the *how*.

Each entry: steps (with commands), result, issues (symptom → cause → fix), lessons.
Append new entries at the end. Paths and versions are exact so a step can be repeated.

Environment for all entries unless stated otherwise: x86_64, Ubuntu 24.04 (glibc 2.39),
32 cores, 30 GB RAM, host ROS 2 Jazzy installed under `/opt/ros/jazzy` (never sourced for Bazel).

---

## 2026-11-08: Import sources as a monorepo

Steps:
1. Start from the vcs-imported workspace (`vcs import src < repositories/*.repos`), every clone clean and non-shallow.
2. Move the clones out of `src/` (here to `.vcs_src/`, excluded via `.git/info/exclude`), and remove the
   placeholder `src/.gitignore` (it ignored everything) and `src/README.md`.
3. For each clone, add it as a squashed subtree from the local clone at its exact HEAD (no network):
   ```bash
   git subtree add --squash --prefix=src/<path> .vcs_src/<path> <sha> \
     -m "chore(src): import <path> <tag-or-sha>" -m "Upstream: <url> @ <sha>"
   ```
4. Verify: `diff -rq --exclude=.git .vcs_src src` prints nothing.

Result: 36 repos, 15,478 files, one squash + one merge commit per repo. Each import commit records upstream URL and SHA.

Lessons:
- `--squash` keeps the repo small (full history would add ~1.2 GB and ~35k upstream commits) while every file stays traceable to an upstream SHA.
- Importing from the local clones (not the URLs) guarantees the tree is exactly what was built before.

## 2026-11-09: P0 bootstrap (host)

Steps:
1. Install bazelisk as `bazel`, verifying the release checksum (the `.sha256` asset holds only the hash):
   ```bash
   gh release download v1.30.0 -R bazelbuild/bazelisk -p bazelisk-linux-amd64 -p bazelisk-linux-amd64.sha256
   [ "$(cut -d' ' -f1 bazelisk-linux-amd64.sha256)" = "$(sha256sum bazelisk-linux-amd64 | cut -d' ' -f1)" ]
   install -m755 bazelisk-linux-amd64 ~/.local/bin/bazel
   ```
2. Workspace files (commit 9aff67c):
   - `.bazelversion`: `9.3.2` (latest 9.x; the RCR requires Bazel 9).
   - `MODULE.bazel`: `bazel_dep` on `ros_core@lyrical.2026-10-05.rcr.0`, plus `rclcpp`, `rosdistro`, `std_msgs` at `0.0.0`
     (MVS resolves them to the ros_core release). Toolchains and rules copied from the RCR examples
     (`llvm@0.8.25.rcr.0` with LLVM 21.1.8, `rules_cc@0.2.26.rcr.0`, `rules_python@2.4.1`, `rules_rs@0.1.0`, `protobuf@36.2`).
   - `.bazelrc`: Linux subset of `BAZELRC_TEMPLATE` in the RCR's `tools/ci/setup_workspace.py` (see issue 2).
   - `bazel/platforms/BUILD.bazel`: platform with `@llvm//constraints/libc:gnu.2.34`.
   - `.bazelignore`: `src` (until packages get BUILD files; `src/universe/external/glog` ships its own BUILD files).
   - `user.bazelrc` (gitignored): machine-local resource limits (see issue 1).
   - `bazel/smoke/`: a `std_msgs` talker using `collect_transitive_dynamic_deps` like the RCR examples.
3. Build and run, always from a clean environment:
   ```bash
   env -i HOME=$HOME PATH=$HOME/.local/bin:/usr/bin:/bin bazel build //bazel/smoke:talker
   env -i HOME=$HOME PATH=$HOME/.local/bin:/usr/bin:/bin bazel run --script_path=/tmp/talker.sh //bazel/smoke:talker
   bash /tmp/talker.sh   # prints "hello from bazel N" every 500 ms
   ```
4. Check the glibc requirement: `objdump -T <binary and its .so files> | grep -oE 'GLIBC_[0-9.]+' | sort -uV | tail -1` → `GLIBC_2.34`.

Result: talker builds (7 min with a matching cache config) and runs on the host with FastDDS (RCR default).
Talker sha256 (host): `b181422b6fa2d86de1054fdb568176fbbfde4b0af036cfad99bfa5c82c32b82c`.

Issues:
1. **OOM crash during the first cold build.**
   Symptom: the machine ran out of memory, the session died.
   Cause: Bazel defaults to one job per core (32) on 30 GB RAM; LLVM-compiled C++ (Qt, Ogre, FastDDS) plus a concurrent `docker build`.
   Fix: `user.bazelrc` with `build --jobs=12`, `--local_resources=cpu=12`, `--local_resources=memory=HOST_RAM*.5`; never run other heavy jobs alongside a cold build.
2. **FastDDS fails to compile** (`invalid application of 'sizeof' to an incomplete type 'eprosima::fastdds::statistics::StatisticsAncillary'`), after 45 min.
   Cause: `.bazelrc` was copied from the RCR's `examples/.bazelrc`, which lacks the per-file C++ standard exceptions. The RCR CI uses the `.bazelrc` generated by `tools/ci/setup_workspace.py`, which compiles fastdds and popf as C++17 and gz-sim as C++20 (C++23 elsewhere).
   How it was found: same module versions (`bazel mod explain fastdds`), no host leakage (`bazel aquery` shows `--sysroot=/dev/null`, no `/usr` paths), RCR CI badges green; then grep the generator.
   Fix: copy the exceptions plus `--action_env=LC_CTYPE/PATH` pins from `BAZELRC_TEMPLATE`.
3. **Low remote cache hit rate.** First run: 1,504 hits of ~23k actions from Intrinsic's cache. After issue 2's fix: 10,746 hits, 2 local compiles.
   Cause: action keys include flags and action env; differing from the RCR CI config means cache misses.
4. **`bazel run` killed by a short `timeout`.** Bazel re-checks the build before running; a 4 s timeout interrupts it.
   Fix: `bazel run --script_path=<file>` once, then run the script.

Lessons (apply to any RCR-based workspace):
- The source of truth for flags is `BAZELRC_TEMPLATE` in `tools/ci/setup_workspace.py`, not `examples/.bazelrc`. Re-check it when bumping the RCR release.
- Match the RCR CI flags exactly to get remote cache hits; a cold build without hits takes ~45 min+ on 12 jobs.
- Set resource limits before the first build on machines with high cores-to-RAM ratios.
- Start Bazel with `env -i` when a ROS distro is installed on the host.

Open: the talker's graph includes Ogre/OpenCV/PySide6 (~93k targets configured). Resolved in "P1: Trim the dependency graph" below.

## 2026-11-09: P0 bootstrap (container)

Steps:
1. `images/dev.Dockerfile`: pinned `ubuntu:24.04` digest, `ca-certificates curl git unzip zip`, bazelisk with checksum check, user `ubuntu` (uid 1000).
2. Build in the container with the host caches mounted, without overwriting the host's convenience symlinks:
   ```bash
   docker build -f images/dev.Dockerfile -t autoware-bazel-dev images
   docker run --rm -v "$PWD":/workspace \
     -v ~/.cache/bazel-disk:/home/ubuntu/.cache/bazel-disk \
     -v ~/.cache/bazel-repo:/home/ubuntu/.cache/bazel-repo \
     -v ~/.cache/bazelisk:/home/ubuntu/.cache/bazelisk \
     autoware-bazel-dev bazel build --experimental_convenience_symlinks=ignore //bazel/smoke:talker
   ```

Issues:
1. **`FATAL: mkdir('/home/ubuntu/.cache/bazel/_bazel_ubuntu'): Permission denied`.**
   Cause: Docker creates missing parent directories of bind mounts as root, so `~/.cache` became root-owned.
   Fix: `RUN install -d -o ubuntu -g ubuntu /home/ubuntu/.cache` before `USER ubuntu`.

3. Run the host-built talker in the container (output base mounted at the same absolute path, so the runfiles paths resolve):
   ```bash
   docker run --rm -e ROS_LOG_DIR=/tmp -v $HOME/.cache/bazel:$HOME/.cache/bazel:ro \
     -v /tmp/talker.sh:/talker.sh:ro autoware-bazel-dev bash /talker.sh
   ```

Result: **P0 done.**
- Container build: 284 s, `12090 disk cache hit, 14057 internal`, 0 local compiles. Host and container produce the same action keys.
- Talker sha256 in the container: `b181422b6fa2d86de1054fdb568176fbbfde4b0af036cfad99bfa5c82c32b82c`, identical to the host build.
- The talker runs in the container (glibc 2.39 base).

Issues (continued):
2. **The talker aborts in a read-only runfiles tree** (`spdlog_ex: Failed opening file .ros/log/... Read-only file system`).
   Cause: the RCR `.bazelrc` sets `--run_env=ROS_HOME=.ros`, relative to the runfiles directory.
   Fix: set `ROS_LOG_DIR` (or `ROS_HOME`) to a writable absolute path. The runtime image (P4) must do this.

Lessons:
- Progress lines name each action ("Compiling ...") and cached compiler warnings are replayed, even for cache hits. Judge cache behaviour by the final `processes:` summary, not by the scrolling output.
- A fresh container repeats analysis (~5 min here) because the output base is not shared. Compiles come from the disk cache.

## 2026-11-09: P0 listener test (FastDDS and CycloneDDS)

Steps:
1. Added `//bazel/smoke:listener` (subscribes to `chatter`), reusing the talker's dynamic deps. Incremental build: 43 s, 2 local actions.
2. The default build (`--@rosdistro//:rmw=dynamic`) contains every RMW; `RMW_IMPLEMENTATION` picks one at runtime.
   The `bazel run --script_path` scripts hard-code `RMW_IMPLEMENTATION=rmw_fastrtps_cpp` (from `--run_env`), so per RMW
   make a copy with the value replaced (`sed`), then run listener first and talker 1 s later, both with
   `ROS_DOMAIN_ID=73 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST ROS_LOG_DIR=<writable dir>` (isolated from the host's Jazzy).

Result (4 s of talker, 7 messages):
- `rmw_cyclonedds_cpp` (Autoware's RMW): 7 sent, 7 received.
- `rmw_fastrtps_cpp`: 7 sent, 2 received. The first five were published before discovery completed; volatile QoS drops them. Expected.

Lessons:
- One dynamic build covers all RMWs; switching is a runtime env var, no rebuild.
- `--run_env` values are baked into `bazel run` scripts and override the caller's environment: set RMW/ROS variables
  in `.bazelrc` (or override in the runtime image), not by exporting them before `bazel run`.

## 2026-11-09: CycloneDDS as default, with the legacy cyclonedds.xml

Steps:
1. `bazel/config/cyclonedds.xml`: exact copy of `docker/files/cyclonedds.xml`.
2. `.bazelrc`: `--run_env`/`--test_env` `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` and
   `CYCLONEDDS_URI=file://bazel/config/cyclonedds.xml`. The path is runfiles-relative (cwd of `bazel run`/`bazel test`),
   so each target lists `data = ["//bazel/config:cyclonedds.xml"]` (to be automatic in `autoware_package()`).
3. `bazel/config/dds_setup.sh`: applies the kernel settings the XML needs in the current context, or exits 1 with one
   clear line per unmet requirement. `host/autoware-dds-setup.service` runs it at boot on a bare-metal/OTA host.
4. Dev image: added `iproute2` (the script uses `ip`).

Result: on the configured host, talker/listener with the XML: 7 sent, 7 received (no discovery-range override).

Issues:
1. **`%workspace%` is not expanded in `--run_env`** (it ends up literally in the run script).
   Fix: runfiles-relative path. An absolute path would also have put the checkout path into test action keys,
   making host (`/home/...`) and container (`/workspace`) keys differ.
2. **CycloneDDS aborts with the XML on a default host**: `failed to increase socket receive buffer size to at least
   10485760 bytes, current is 8388608` → `rmw_create_node: failed to create domain`; also `selected interface "lo" is not
   multicast-capable: disabling multicast`.
   Cause: the XML (`SocketReceiveBufferSize min="10MB"`, multicast on `lo`) assumes host tuning from the Autoware DDS
   settings guide; the legacy ansible does not apply it.
   Fix: `net.core.rmem_max=2147483647`, `net.ipv4.ipfrag_time=3`, `net.ipv4.ipfrag_high_thresh=134217728`, `ip link set lo
   multicast on` (applied on this host via sysctl.d + a systemd unit; now `dds_setup.sh` + `host/autoware-dds-setup.service`).
3. **Can a container apply these itself?**
   - `net.core.rmem_max`: machine-wide. `docker run --sysctl net.core.rmem_max=...` is refused (`open sysctl ... permission
     denied`); `CAP_NET_ADMIN` does not help (CycloneDDS does not use `SO_RCVBUFFORCE`). Only a privileged container
     (which writes the host kernel) or host setup. Privileged container not tested (blocked by the agent permission check).
   - `lo` multicast: needs `CAP_NET_ADMIN` in the namespace the nodes run in (verified: own netns + `--cap-add NET_ADMIN`
     turns it on).
   - `net.ipv4.ipfrag_*`: per namespace, `docker run --sysctl` works.
4. **Docker on this dev machine is Docker Desktop** (containers run in a `linuxkit` VM, kernel 7.0.14-linuxkit), not
   Docker Engine. Containers, even with `--network host`, see the VM's kernel settings and loopback, not the host's.
   Container results about kernel settings therefore describe the VM. Build results (P0 digests) are unaffected.

Lessons:
- DDS config files carry host requirements. Ship the XML together with a check script that fails loudly, instead of
  letting the RMW abort with `failed to create domain`.
- On the vehicle (Docker Engine, host network), the boot service or a privileged entrypoint applies the settings to the
  device itself; on a shared dev machine, prefer the host service.
- Check `docker info` (`OperatingSystem`) before drawing kernel/network conclusions from containers: Docker Desktop
  inserts a VM. It also lacks `--gpus` support on Linux, which P3/P4 need.

## 2026-11-09: Cost of a runtime config as a `data` dependency

Steps: build `//bazel/smoke:all`, change a value in `bazel/config/cyclonedds.xml` (`WhcHigh` 500kB -> 600kB), rebuild
with `--explain=<file>`, revert.

Result: the rebuild executed no actions (only the unconditional `BazelWorkspaceStatusAction`). Runfiles entries for
source files are symlinks, so editing a `data` file does not recompile, relink or copy anything. Tests that list it
re-run, because it is a test input.

Decision (PLAN.md, "Rules needed"): keep `data = ["//bazel/config:cyclonedds.xml"]` explicit for now; a wrapper rule
that attaches it implicitly is deferred until its contents are clear.

Lesson: a shared runtime config can be a `data` dependency of every binary and test without hurting incremental builds.
The cost is boilerplate, not build time.

## 2026-11-09: P1 start: trim the dependency graph (static CycloneDDS)

Steps:
1. Find why a talker pulls Ogre:
   ```bash
   bazel cquery 'somepath(//bazel/smoke:talker, @@ogre+//...)'
   ```
   → `rclcpp → rcl → rmw_implementation_dynamic_library → :ament_index → @rmw_fastrtps_dynamic_cpp//:ament_package
   → @rosdistro//:ament_package → @rosdistro//cc:RenderSystem_GL3Plus → @ogre`.
   `@rosdistro//:ament_package` bundles every third-party shared library and every pip package of the distribution
   (it builds a self-contained install tree). With `--@rosdistro//:rmw=dynamic` (the RCR default), the RMW loader's
   ament index depends on all RMWs' `ament_package` targets, and through them on that catch-all.
2. With `--@rosdistro//:rmw=rmw_cyclonedds_cpp`, `rmw_implementation` is a plain alias to the CycloneDDS library and the
   edge disappears. Measured with `bazel cquery 'deps(//bazel/smoke:talker)' | wc -l`: 89,186 → 19,268 targets.
3. `.bazelrc`: `build --@rosdistro//:rmw=rmw_cyclonedds_cpp`, plus `--config=rmw_dynamic` to restore runtime switching.

Result: switch-over build 152 s (140 local actions: the rcl/rclcpp chain relinks against CycloneDDS directly); talker/
listener 7/7; cold-server analysis of `//bazel/smoke:all` 46 s (was ~5 min).

Lessons:
- In the RCR, anything that depends on the dynamic RMW loader inherits the whole distribution. Pick the RMW at build time
  unless runtime switching is needed.
- `bazel cquery 'somepath(<target>, @@<repo>+//...)'` is the quickest way to explain an unexpected dependency.

## 2026-11-09: P1 interface packages (module per ROS package)

Steps:
1. Studied how RCR declares interface packages (`modules/<pkg>/<ver>/overlay/` in the RCR repo):
   root `BUILD.bazel` with `default_generators(dependencies = ["@dep_pkg", ...], package_xml = "package.xml",
   deps = ["//msg:X", ...])`, and `msg/BUILD.bazel` (`srv/`, `action/`) with one `ros_message`/`ros_service`/
   `ros_action` per file and per-interface `deps`.
2. Found that `core_generators` derives the ROS package name from `native.module_name()` (overridable with
   `export_name`) and takes `dependencies` as repository labels (`"@std_msgs"` → `@std_msgs//:cc_shared`). In-repo
   labels (`//src/...`) break both. Decision: one Bazel module per ROS package (PLAN.md "Package conventions"):
   `src/.../<pkg>/MODULE.bazel` + root `bazel_dep(name = "<pkg>")` + `local_path_override(path = "src/...")`.
   `local_path_override` works even though `src` is in `.bazelignore`.
3. Prototype by hand (`autoware_common_msgs`, `autoware_localization_msgs`), verified with `//bazel/smoke:interfaces_test`
   (includes generated headers, checks `rosidl_generator_traits::name<>()`, uses a cross-package field).
4. Migration aid `//bazel/tools/gen_build:gen_interfaces` (stdlib Python, run with `bazel run`): parses field types of
   every `.msg/.srv/.action` (arrays, bounded strings, bare `Header`, same-package types), writes `MODULE.bazel`,
   root `BUILD.bazel`, and a `BUILD.bazel` per interface directory, for packages without a `MODULE.bazel`; rewrites
   `bazel/autoware_packages.MODULE.bazel` (included by the root `MODULE.bazel` via `include()`) and
   `bazel/autoware_packages.txt` (for `--target_pattern_file`). Parser covered by `gen_interfaces_test`.
   The written files are hand-maintained afterwards (no "generated" header); the tool never overwrites them.
5. Ran it on `src/core`: 23 interface packages, ~250 interfaces (incl. `autoware_adapi_v1_msgs` with `<group>/msg/`
   directories, `agnocast_*`, `negotiated_interfaces`).
6. Build: `bazel build --target_pattern_file=bazel/autoware_packages.txt`.

Result: all 23 packages build (C, C++, Python bindings). Last full build 755 s, 2,940 local actions.

Issues:
1. **`autoware_motion_velocity_planner` is in `rosidl_interface_packages` but has no interface files** (stale
   declaration). Fix: detect interface packages by their files, not by the `package.xml` group.
2. **`no such package '@@geographic_msgs+//msg'`.** Cause: `0.0.0` resolves to a real version only if some module pins
   it; `ros_core` (and the variant modules) do not pin `geographic_msgs`, so MVS picked the RCR's empty `0.0.0` stub.
   Fix: depend on the top-level `ros@lyrical.2026-10-05.rcr.0` module, which pins the whole distribution (1,860
   modules: also lanelet2, pcl_ros, generate_parameter_library, point_cloud_msg_wrapper, ...). Lockfile 8.5k → 11.7k
   lines; first resolution 2.5 min.
3. **`crate_universe` extension fails: `Unable to load package for //:MODULE.bazel`** after the `ros` pin.
   Cause: rules_rust resolves `@@//:MODULE.bazel`, which requires a root package. Fix: empty root `BUILD.bazel`.
4. **Python test cannot import the module under test** (`No module named 'gen_interfaces'`).
   Fix: import by workspace path, `from bazel.tools.gen_build.gen_interfaces import ...`.
5. `bazel test --target_pattern_file=... //other:target` is rejected (cannot combine both); concatenate into one file.

Lessons:
- With the RCR, make each ROS package its own Bazel module; its rules assume module name = package name.
- Depend on the top-level `ros` release module, not `ros_core`, or packages outside the core variant resolve to stubs.
- Generate the first BUILD files mechanically from `package.xml` and interface files, then treat them as sources.

## 2026-11-09: P1 C++ packages (autoware_utils) — P1 done

Steps:
1. RCR C++ package pattern (e.g. `tf2_eigen` overlay): `cc_library(name = "<pkg>_library", includes = ["include"],
   local_defines = ros_local_defines())` + `cc_shared_library(name = "<pkg>", dynamic_deps = DEPENDENCIES.keys(),
   exports_filter = [":<pkg>_library"])`, where `DEPENDENCIES = {"@x//:x": "@x//:x_library", "@m//:cc_shared": "@m//:cc"}`;
   tests use `collect_transitive_dynamic_deps` and `@rosdistro//cc:googletest`; third-party libs via `@rosdistro//cc:*`
   (`eigen`, `fmt`, `boost.<component>`, `pcl_common`, ...).
2. Migration aid `//bazel/tools/gen_build:gen_cc -- <pkg dirs>` for the `ament_auto_add_library(${PROJECT_NAME} SHARED ...)`
   shape: ROS deps from `package.xml`, third-party targets from `#include`s, tests from `test/**/*.cpp`; warns about
   included-but-undeclared ROS packages. Applied to the 12 `src/core/autoware_utils/*` packages.
3. Build/test: `bazel test --keep_going --target_pattern_file=<list of @autoware_utils_*//...>`.

Result: all 12 packages build; 11 test suites pass (the umbrella `autoware_utils` is header-only, no tests).
Together with the 23 interface packages: `bazel test --target_pattern_file=bazel/autoware_packages.txt` + `//bazel/...`
→ 13 tests pass. A cold build of the PCL-dependent chain took ~55 min (PCL from source).

Issues (symptom → cause → fix):
1. `unknown repo 'rules_cc' requested from @@autoware_utils_debug+` → a module sees only repos it declares →
   `bazel_dep(name = "rules_cc", ...)` in every package module.
2. `@googletest` invisible despite `bazel_dep(..., dev_dependency = True)` → dev dependencies of non-root modules are
   ignored → plain `bazel_dep`.
3. `glob pattern 'include/**/*.h' didn't match anything` → Bazel 9 disallows empty glob patterns → emit only matching
   patterns; list test headers/data explicitly.
4. Duplicate `main()` risk → `@rosdistro//cc:googletest` includes `gtest_main`; 10 of 12 packages have their own
   `test/main.cpp` (for `rclcpp::init`) → use `@googletest//:gtest` there (`googletest@1.18.0.bcr.1`, as resolved).
5. `'std_msgs/msg/string.hpp' file not found` (autoware_utils_debug) → header uses a package not declared in
   `package.xml`; colcon resolves it transitively → declared the missing deps in `package.xml` (commit 6fde311:
   debug: std_msgs, rosidl_runtime_cpp; geometry: geometry_msgs, autoware_perception/planning_msgs; pcl: rclcpp).
6. `no such target '@@tf2_geometry_msgs+//:cc'` / `'@@logging_demo+//:logging_demo'` → package type guessed from the
   name suffix → override table (`tf2_geometry_msgs` is C++; `logging_demo` provides the `ConfigLogger` service, `:cc`).
7. `no such target '@@rosdistro+//cc:boost.version'` → `boost/version.hpp` belongs to `boost.config`.
8. `Two shared libraries in dependencies link the same library statically. Both autoware_utils_geometry and
   @rosdistro//cc:boost.serialization_shared link statically @boost.serialization` → `boost.geometry` pulls compiled
   Boost libs that end up static in our shared library, while PCL provides them shared → list
   `boost.{chrono,container,serialization,thread}_shared` pairs in `DEPENDENCIES` (hand edit, as the RCR does).
9. `autoware_utils_pcl` → `pcl_ros` targets are split (`pcl_ros_tf`, `pcl_ros_filter`) → headers only need
   `pcl_conversions` + `@rosdistro//cc:pcl_common`; dropped `pcl_ros` from the BUILD/MODULE (hand edit).
10. Deleting a package's `MODULE.bazel` while `bazel/autoware_packages.MODULE.bazel` still lists it blocks every
    `bazel` command, including `bazel run` of the migration aid → run the stdlib-only tools as
    `python3 -m bazel.tools.gen_build.<tool>` from the repo root.

Discovery: the RCR already contains 36 Autoware modules (all autoware_msgs, internal/adapi msgs, autoware_utils_*,
autoware_lanelet2_extension) at their ROS-released versions, with hand-written overlays. Our `local_path_override`s
win everywhere; their overlays (`modules/<pkg>/<ver>/overlay/BUILD.bazel` in the RCR repo) are the best reference for
porting the rest.

Lessons:
- Bazel's strict dependency checking finds real upstream bugs (undeclared deps). Fix them in `package.xml`.
- Before writing a BUILD file for a ROS package, check whether the RCR already has an overlay for it.
- Header-only Boost components can drag compiled Boost libraries into your shared library; link those shared.

## 2026-11-09: P2 start — `autoware_package()` settings as a Bazel module; `gen_cc` dropped

Review of `gen_cc` against the 12 `autoware_utils` CMakeLists.txt: sources and tests matched, but it missed
everything `autoware_package()` sets (`-Wall -Wextra -Wpedantic -Werror`, `-std=c++17`,
`BOOST_ALLOW_DEPRECATED_HEADERS`, `EIGEN_DONT_PARALLELIZE`), and of the 73 `autoware_core` CMakeLists.txt, 12 register
components, 5 add executables and 36 install launch/config, none of which it handled. Deleted; C++ BUILD files are
written by hand from CMakeLists.txt from now on.

Steps:
1. `src/core/autoware_cmake/autoware_cmake/{MODULE.bazel,BUILD.bazel,defs.bzl}`: module `autoware_cmake` exporting

## P3: CUDA toolchain routes (LLVM 23 parked on `bazel-llvm23`)

Goal: CUDA declared and versioned in Bazel, replacing ansible/roles/cuda and tensorrt; only the GPU driver stays on
the host. Hermetic toolkit: rules_cuda `cuda.redist_json(version, sha256)` in `bazel/cuda.MODULE.bazel`. The
manifest pins every component archive for linux-x86_64 and linux-sbsa. Problem: compiling `.cu` with the build's
clang 21 + libc++ 21.

What was found:
1. RCR rules_cuda 0.3.0.rcr.0 rejects `sm_110` (Thor) → `bazel/patches/rules_cuda_sm110.patch` (upstream has it).
2. nvcc 13.0 + host clang 21: CUDA 13.0 accepts clang < 21 and refuses libc++ on x86 (both overridable). Then nvcc's
   EDG front end fails on libc++ 21 (`__builtin_common_type is not a template`, `std::__promote`).
3. clang 21 as CUDA compiler: CUDA ≤ 12.8 (`texture_fetch_functions.h` not found with CUDA 13), no `sm_110`.
4. **Route A, LLVM 23.1.2 for everything** (clang compiles CUDA; clang 23 supports CUDA ≤ 13.2 and `sm_110`).
   Measured in a separate worktree: the first build took 2 h 22 min cold, then 6 pass / 188 fail to build. After
   wave-1 fixes (5 third-party patches, 1 flag, 2 source fixes), 146 pass, 35 fail to build, 1 fails. libc++ 23 dropped
   transitive includes (rosidl_runtime_cpp, Fast DDS, libzmq, bison, PCL), clang 23 errors on C pointer mismatches
   (OSQP) and reports more `[[nodiscard]]`/deprecation warnings. **lanelet2_utils returns succeeding lanelet sequences
   in another order** (a behaviour change, not a build break). Parked as one commit on branch `bazel-llvm23`; its
   `docs/bazel/LLVM23.md` lists everything done and still needed.
5. JetPack 7.2.1 (current, Thor) ships **CUDA 13.2.2 + TensorRT 10.16.2** (JetPack 7.0: 13.0.0 + 10.13.2.6).
   CUDA 13.2 accepts **clang < 22** as nvcc host compiler, and nvcc 13.2's front end parses libc++ 21 (item 2's errors are
   gone). Left: CUDA's `crt/math_functions.h` uses libc++'s pre-21 `std::__promote` on Linux (its libc++ ≥ 21 branch is
   enabled only for Android/HORIZON); a force-included shim cannot fix it, because nvcc parses its runtime headers first.
   → **Route B**: keep LLVM 21, nvcc 13.2 with host clang 21, patch that CUDA header (needs component patching in
   rules_cuda).

Lessons:
- A compiler/standard-library upgrade is not only a build change. One libc++ upgrade reordered results of a planning
  utility. Run the full test suite before accepting one, and treat order changes as findings.
- Check what the target platform ships (JetPack) before pinning versions from older provisioning scripts.

## P3 route B (branch `bazel-llvm21`): hermetic CUDA 13.2 with nvcc and host clang 21

Toolkit (`bazel/cuda.MODULE.bazel`, included from the root module):
- `cuda.redist_json(version = "13.2.2", sha256 = <sha256 of redistrib_13.2.2.json>)`. The manifest pins every
  component archive, for linux-x86_64 and linux-sbsa. Components: cccl, crt, cudart, culibos (needed by the static
  cudart in 13.x), nvcc, nvvm, plus the libraries the apt role installs (cublas, curand, cusparse, npp, nvjpeg,
  nvml, nvrtc). 13.2.2 is what JetPack 7.2.1 ships for Thor.
- `.bazelrc`: `--@rules_cuda//cuda:compiler=nvcc`, archs `sm_75/86/87/89/110/120 + compute_120` (Autoware's CMake
  list for CUDA >= 12.8), `-D_ALLOW_UNSUPPORTED_LIBCPP` (NVIDIA's policy check against libc++ on x86).
- Package modules see the toolkit through `cuda = use_extension("@rules_cuda//cuda:extensions.bzl", "toolchain")`
  and `use_repo(cuda, "cuda")`; only the root module configures it.

Patches (root `single_version_override` of rules_cuda 0.3.0.rcr.0, and `cuda.component_patch`):
1. `rules_cuda_sm110.patch`: `sm_110` (Thor) is missing from the arch list.
2. `rules_cuda_component_patches_{repositories,extension}.patch`: a new `cuda.component_patch(component, patches)`
   tag; the component repository rule applies the patches after extraction, on every redist platform. Two files,
   because Bazel's patch parser misreads a multi-file diff that GNU `patch` applies (`CONTENT_DOES_NOT_MATCH_TARGET`
   for the second file).
3. `cuda_crt_libcxx_math_functions_{h,hpp}.patch`: CUDA's math headers support libc++ only in branches enabled for
   Android/HORIZON. Defines `__NV_LIBCPP_LINUX` (libc++ on Linux, not Android) and enables three of those branches:
   - the libc++ >= 21 `pow(_A1, _A2)` declaration (`std::__promote_t`; the Linux branch used the removed `std::__promote`);
   - `isnan(long double) noexcept`;
   - the libc++ classification-function block (`signbit/isfinite/isnan/isinf`). Without it they collide with libc++'s
     `using` declarations.
   The branches that concern Android's C library (bionic) are not touched. The SBSA headers are byte-identical, and
   both patches dry-run cleanly on them.

Packages: `autoware_cuda_dependency_meta` (no code, see BUILD comment) and `autoware_cuda_utils` (header-only
CCCL/cudart wrapper, `.cu` tests through `cuda_library`).
```
bazel test @autoware_cuda_utils//...   # 17 tests run on the GPU (RTX 5070, sm_120), all pass
```
The whole suite is unchanged (193 others pass): swapping the auto-detected `/usr/local/cuda` for the hermetic
toolkit rebuilt nothing already ported.

Issues (symptom → cause → fix):
1. `no such target '@cuda//:culibos_a'` → CUDA 13's static cudart needs the separate culibos component → add it.
2. `unknown repo 'cuda' requested from @@autoware_cuda_utils+` → each module must `use_repo` the extension's `cuda`.
3. `'thrust/count.h' file not found` (plain C++ compile) → CUDA 13 moved CCCL to `include/cccl/`; depend on
   `@cuda//:thrust`, `:cub`, `:libcudacxx` (they carry that include path), not `:cccl_headers`.
4. `compute_110 is not a supported cuda arch` → patch 1.
5. `This test program does NOT link in any test case` (test "passed" with 0 tests) → gtest cases in a static
   `cuda_library` are dropped by the linker → `alwayslink = True`. Check the test count, not only the status.
6. nvcc 13.0 failures (clang >= 21 refused; EDG cannot parse libc++ 21), see "P3: CUDA toolchain routes": gone with
   13.2, whose nvcc accepts host clang < 22 and parses libc++ 21.

Parity checker: `cuda_add_executable`/`cuda_add_library` count sources; `ament_add_gtest_test(target)` turns that
executable into a test; `INTERFACE` libraries map to `cc_library`; `include`, `ament_find_gtest` and `return` are
ignored (`return()` only appears under a reported `if()`).

## TensorRT (module `tensorrt`) and autoware_tensorrt_common

TensorRT is closed source, so it comes as NVIDIA binaries, like the CUDA toolkit. Source: NVIDIA's CUDA apt
repository (`ubuntu2404/{x86_64,sbsa}`), the same packages ansible/roles/tensorrt installs. The tar releases are
7.6 GB (x86_64) / 5.6 GB (aarch64), against ~1.9 / 2.3 GB for the needed .debs.
- `bazel/third_party/tensorrt/pins.bzl` is generated by `update_pins.py <version>` from the repository index:
  per CPU, the URL + sha256 of `libnvinfer10`, `libnvinfer-plugin10`, `libnvonnxparsers10` and the headers-only
  `libnvinfer-headers-dev`, `libnvinfer-headers-plugin-dev`, `libnvonnxparsers-dev`. The `libnvinfer-dev` package
  (3 GB of static libraries) is skipped.
- Version **10.16.1.11-1+cuda13.2**. JetPack 7.2.1 ships 10.16.2, which is not in the public repository (nor as a
  tarball: no 10.16.2 build numbers 1–400 exist). Patch level only; engines are built on the target.
- The module extension makes one repository per CPU (`tensorrt_x86_64`, `tensorrt_aarch64`), fetched lazily, plus
  `tensorrt_paths` (runfiles library directories, computed from the canonical name so that loading it fetches no
  .debs). `@tensorrt//:tensorrt` selects by CPU; `@tensorrt//:defs.bzl` has `TENSORRT_VERSION_MAJOR` and
  `tensorrt_test_env()`.

autoware_tensorrt_common: `bazel test @autoware_tensorrt_common//...` → 13 tests pass, including TensorRT engine
builds from `test/data/dummy_network.onnx` on the GPU (RTX 5070, ~23 s). This shows that TensorRT (built with GCC,
using libstdc++) works from our libc++ code. Its API passes TensorRT's own interface types, not `std::` objects.

Issues (symptom → cause → fix):
1. Empty repository; `glob 'usr/include/...' didn't match` → Bazel's `deb` archive type only unpacks the `ar` layer
   (`control.tar.xz`, `data.tar.xz`), and each .deb overwrote the previous `data.tar.xz` → extract each .deb as
   `ar` into its own directory, then `rctx.extract()` its `data.tar.*`.
2. `libraries were linked statically by different cc_shared_libraries but not exported: ...culibos_a` → CUDA 13's
   static `libculibos.a` (a separate component) lacks the `LINKABLE_MORE_THAN_ONCE` tag that the RCR's rules_cuda
   patch gives `cudadevrt_a` → `bazel/patches/rules_cuda_culibos_linkable.patch`.
3. `implicit instantiation of undefined template 'std::basic_ostringstream<char>'` → missing `<sstream>` (libc++).
4. `'experimental/filesystem' file not found` → upstream checks `__GNUC_MAJOR__`, which does not exist, so it always
   chose `<experimental/filesystem>` (libstdc++ has it, libc++ does not) → `#if __has_include(<filesystem>)`.
5. `delete called on non-final 'TrtCommon' ... non-virtual destructor` (-Werror) in the test → CMake's
   `target_compile_options(PRIVATE -Werror ...)` applies to the library only → the test gets default flags.
6. Test segfault (exit 139) while building an engine → `libnvinfer` `dlopen()`s
   `libnvinfer_builder_resource_<sm>.so.<ver>` by bare name. Only `LD_LIBRARY_PATH` and the system directories apply
   (an apt install has them in `/usr/lib/<triple>`). They cannot be linked: each NEEDS a deliberately missing
   `do_not_link_against_nvinfer_builder_resource_*`. A `-Wl,--disable-new-dtags` on `@tensorrt` reached only the
   package's shared library, not the executable. → tests that load TensorRT get `data = ["@tensorrt//:runtime_libs"]`
   and `env = tensorrt_test_env()` (LD_LIBRARY_PATH = the runfiles library directory). The runtime image (P4) installs
   them on the default search path.
7. Loading `tensorrt_test_env()` fetched the aarch64 .debs (2.3 GB) on x86, because `defs.bzl` loaded both per-CPU
   repositories → the separate `tensorrt_paths` repository.

**Host dependency:** `libnvinfer*.so` NEED `libstdc++.so.6` and `libgcc_s.so.1`, which come from the host (Ubuntu
always has them), not from Bazel. So "only the GPU driver comes from the host" does not hold for TensorRT; pin a
libstdc++ for the runtime image (P4).
